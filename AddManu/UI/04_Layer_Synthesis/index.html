    04 Layer Synthesis — AI 專用程式說明

    對應內部 stage.id: part-manufacturing。本文根據使用者提供之十支程式原始檔與原總說明拆分，保留來源描述，不臆測外部數據。

    AI 閱讀與修改準則

    • 本文件對應 2026-10-10 上傳的程式版本，是閱讀程式和修改功能用的索引，不表示外部 NPZ/STL/CSV/NPY 已驗證存在。
    • 先依 stage-data.js 的 stage.id 確認模組，再追 app.js 的階段分支、run_dashboard.py 的 API、viewer 和 HTML/CSS。
    • 優先保留原始資料、欄位、單位與 API 契約；畫面示意、靜態預設指標不可當成真實運算成果。
    • 僅修改本階段必要檔案；共用檔案修改後，必須確認其他五個階段不受影響。
    • 注意 04／05 名稱交叉：04 的 ID 是 part-manufacturing，側欄名稱是 Layer Synthesis；05 的 ID 是 layer-synthesis，側欄名稱是 Part Manufacturing。不要自行對調。

    04（part-manufacturing）— 表面 STL 與逐層 NPZ

    注意：側欄名稱顯示為 Layer Synthesis，程式中 stage.id 仍是 part-manufacturing；app.js 此分支標為「04」。

    目標與畫面

    中央採左右雙視圖。左側支援逐層 NPZ 的 Surface Texture / 表面偏差資料，搭配 STL 顯示；可使用 layer 滑桿。右側是 STL 上表面高度／Surface Ra 色階檢視；右側分析區呈現表面高低差等結果。切換此頁時會隱藏一般 NPZ Track、Melt Pool iframe 與 05 的 layer melt host。

    資料源

    • PART_MANUFACTURING_STL_PATH：預設沿用 LAYER_STL_PATH，可用 LPBF_PART_MANUFACTURING_STL 覆寫。
    • PART_MANUFACTURING_NPZ_DIR：預設 E:\CHEN_Yu_Yang\DASH_HTML\data\npz，可用 LPBF_PART_MANUFACTURING_NPZ_DIR 覆寫。
    • PART_MANUFACTURING_NPZ_GLOB：預設 layer_xy_prediction_L*.npz。
    • 逐層掃描與滑桿通常對應 L0001–L0250，但實際可用層數以 API 回傳為準。
    • PART_MANUFACTURING_SURFACE_DX_UM / DY_UM / DZ_UM 預設各 2.0 µm，是此頁表面處理的設定值，勿反向推定所有輸入檔的真實精度。

    API

    • /part-manufacturing-stl、/api/part-manufacturing-stl-info
    • /api/part-manufacturing-npz/meta
    • /api/part-manufacturing-npz/layer?layer=N

    上表面判定

    後端先產生 XY top-envelope，再以 deterministic RANSAC 搜尋具有足夠面積支撐的最高平面；由種子定位對應連通 component，保留完整上表面區域，過濾少量孤立點。自動偵測失敗時才走中央種子 fallback。其假設是模型建造高度沿 STL Z 軸，如果 STL 側躺，先校正方向。

    重要區別：Surface ΔH = max(Z) − min(Z) 是高度範圍；Ra 是算術平均粗糙度的定義，兩者不是同一指標。UI 文字、顏色或標籤不得把 ΔH 直接改寫為 Ra。

    AI 修改禁忌

    • 左右 Viewer 不可合併成單一資料源；右側 STL 色階需與後端上表面結果一致。
    • 切換 layer 應刷新對應 layer 資料；不可只換 L000x 標籤。
    • 對其他工件更換 STL 時，確認 Z-up、單位、RANSAC 選面和高度計算。

    API 快速索引

    /api/part-manufacturing-npz/{meta,layer}；/api/part-manufacturing-stl-info

    上述大括號表示路由集合的說明用縮寫，並非完整 URL；請依 run_dashboard.py 的實際路由與參數呼叫。

    請先閱讀本文件與同版本程式，確認 part-manufacturing 的實際資料來源、前端分支、API 和畫面元件，再修改第 04 階段。不得以其他階段資料取代本階段真實輸入；不得把前端示意或顯示校正寫成求解器結果。修改後說明涉及的函式、檔案、單位、資料格式和對其他五階段的相容性。

    AI 判讀來源的優先順序與防誤讀

    1. 目前程式有什麼：查 stage-data.js 的 number、id、name，再查 app.js 分支以及 run_dashboard.py 真正路由和輸入資料。
    2. 外部網站怎麼命名：採用對應 Additive Manufacturing 頁面的 01–06 階段順序；網站沒有細節的地方標示「未說明」，不要補寫成網站宣稱。
    3. 哪些是示意／靜態值：先辨別 stage-data.js 靜態 metrics、進度條與 log，不能把候選或 placeholder 數字當成模擬驗證。
    4. 如何修改：先確認牽涉的函式、前端欄位、HTTP 回傳、NPZ／STL／CSV 結構與單位，再修改。不要根據網站章節標題自行新增不存在的 Web Service 呼叫。
    5. 如何驗證：檢查本階段載入、API 回應、空資料／缺檔提示、視覺化與右側 metrics；共用元件變更時回歸檢查 01–06。
