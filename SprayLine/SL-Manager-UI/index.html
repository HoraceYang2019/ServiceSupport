    Spray Line Manager UI 使用說明書

    適用範圍：final_version_0718_v3/
    程式基準：a9550494ad27d19dbd0079349fbc1cd2660d0dc1
    使用角色：Manager、Primary Engineer、Collaborator
    文件版本：2026-10-21

    本手冊從使用者角度說明 Manager UI 的畫面、操作順序、狀態變化與異常處理。畫面截圖由專案原始 HTML、CSS 與 JavaScript 實際渲染；Dashboard 數值取自倉庫附帶的 sample_manager_dashboard.json，任務與人員名稱使用符合現行 API contract 的示範資料，不代表現場正式紀錄。

    1. Manager UI 是做什麼的

    Manager UI 將三個噴塗站的資料整理成主管容易判讀的資訊。Manager 可以用它完成四件主要工作：

    1. 選擇日期、小時與批次，查看指定時間範圍的資料。
    2. 比較三個站點的稼動率、預估 OK／NG 數量與主要問題。
    3. 從系統建議建立工程師任務，指定 Primary 與 Collaborator。
    4. 追蹤工程師是否收到、是否開始處理、回報了什麼，以及是否完成驗收。

    Manager UI 不直接控制機台，也不直接讀取感測器。它顯示的是 Main API 整理後的資料，正式任務狀態則保存在 PostgreSQL。

    2. 整體操作流程

    flowchart LR
    A[選擇日期／小時／批次] --> B[查看 KPI 與三站比較]
    B --> C{是否出現需處理項目}
    C -- 否 --> D[持續監看或切換時段]
    C -- 是 --> E[查看問題與系統建議]
    E --> F[選擇工程師並建立任務]
    F --> G[工程師 ACK 並開始處理]
    G --> H[填寫現場回報與附件]
    H --> I[Primary 提交完成]
    I --> J{Manager 驗收}
    J -- 通過 --> K[任務完成]
    J -- 退回／重開 --> G

    日常使用時，可以把流程記成：「先選時間，再看異常；有異常就派工；工程師回報後由 Manager 驗收。」

    3. 頁面關係

    flowchart TD
    DASH[Manager Dashboard]
    TREND[Trend Drawer]
    ASSIGN[工程師選擇 Dialog]
    HISTORY[通知紀錄]
    TASKLIST[工程師任務清單]
    DETAIL[任務明細 Dialog]
    TOKEN[Engineer Token 工作頁]

    DASH -->|點擊趨勢圖示| TREND
    DASH -->|點擊發送通知| ASSIGN
    DASH -->|通知紀錄與工程師任務| HISTORY
    HISTORY -->|切換頁籤| TASKLIST
    TASKLIST -->|明細| DETAIL
    ASSIGN -->|建立任務與安全連結| TOKEN
    TOKEN -->|回報與狀態更新| DETAIL

    4. Manager Dashboard

    Dashboard 由上到下分為 Header、主管重點指標、三站狀態比較表及需要處理的項目。

    4.1 Header：切換資料時間

    Header 左側是頁面名稱，以及「通知紀錄與工程師任務」入口。右側有 Date 與 Hour：

    1. Date 只列出資料庫有資料的日期。
    2. DB latest 代表目前資料庫中的最新日期。
    3. Hour 只列出該日期有資料的小時區間。
    4. 改變 Date 或 Hour 後，Dashboard 會重新向 API 取得整份資料。

    查看歷史資料時，應先確認 Date，再確認 Hour。畫面載入時間不是資料發生時間；真正的資料範圍以這兩個欄位為準。

    4.2 主管重點指標

    畫面顯示四個摘要：

    • 估算 OK rate：依選定日期的感測資料估算，不等同正式品檢良率。
    • 估算 NG rate：以 100% - 估算 OK rate 計算，用於快速比較風險。
    • 今日產能達成率：以批次數、每批件數及每日目標估算。
    • 目前最嚴重站點：指出目前優先注意的站點、製程與主要問題。

    這些數字是管理判讀指標。若要確認實際良率或根因，仍需搭配品檢紀錄與工程師現場回報。

    4.3 三站狀態比較表

    三站比較表讓 Manager 在同一畫面比較：

    • Station 與 Process。
    • 稼動率。
    • 預估 OK pcs。
    • 預估 NG pcs。
    • 主要問題。

    右上方 Batch 可切換「全部批號／該小時累計」或單一批次。切換 Batch 後，後端會重新計算同一組 KPI、站別比較與診斷結果，不是只在前端過濾既有文字。

    4.4 查看趨勢圖

    稼動率、預估 OK pcs 與預估 NG pcs 旁都有趨勢圖示。點擊後會從右側打開 Trend Drawer。

    Trend Drawer 包含：

    1. 站點、製程與指標名稱。
    2. 目前模式，例如全部批號或指定批次。
    3. 今日平均／累計、本小時及最高小時摘要。
    4. 00 至 23 時的趨勢線。

    圖上沒有資料的時段不會自動當成 0。若整條序列都沒有有效值，畫面會顯示沒有可用趨勢資料，避免把缺測誤認為零產出。

    4.5 需要處理的項目

    此區是後端依風險規則產生的 Recommendation。每張項目卡會顯示站點、製程、主要問題、建議與風險等級。

    Manager 應先閱讀問題與建議，再決定是否按「發送通知」。系統建議是檢查方向，不代表已經確認根因。

    5. 建立工程師任務

    在 Recommendation 按下「發送通知」後，系統會先查詢該站目前有效的工程師指派，再開啟選擇視窗。

    5.1 選擇規則

    • 左側勾選框決定哪些工程師加入任務。
    • Primary 單選鈕決定主要負責人，且 Primary 必須是已勾選的人員。
    • 「必要參與」表示此工程師是任務必要成員。
    • Collaborator 可協助回報，但只有 Primary 能提交整體完成。

    確認後按「建立並寄送」。後端會建立 Task、Assignee、安全 Token、寄送狀態及第一筆 Timeline 事件。成功後，任務可在通知紀錄頁追蹤。

    5.2 建立前檢查

    送出前請確認：

    1. 站點與製程是否正確。
    2. Primary 是否為真正負責處理的人員。
    3. 必要參與者是否完整。
    4. Recommendation 內容是否符合目前時段與批次。

    若站點沒有正式工程師指派，系統可能詢問是否使用舊 Email fallback。正式環境應優先維護站別工程師指派，不應把 fallback 當成主要流程。

    6. 通知紀錄

    從 Dashboard Header 點擊「通知紀錄與工程師任務」，會進入通知紀錄頁。預設頁籤為「通知決策」。

    6.1 篩選條件

    可依起日、迄日、小時、站別、批次、決策、寄送狀態、流程狀態、工程師 Email 或 Task ID 查詢。條件留白代表不限制該欄位。

    6.2 決策結果怎麼看

    • email_task_created：異常已建立工程師任務並寄送通知。
    • dashboard_only：只顯示在 Dashboard，尚未建立 Email 任務。
    • suppressed：相同異常在抑制窗口內，避免重複通知。
    • cooldown_skipped：仍在冷卻時間內，因此本次不重複建立通知。

    「抑制次數」不是錯誤次數，而是同一異常被重複判定後，系統避免重複通知的累積數量。

    7. 工程師任務清單

    切換到「工程師任務」頁籤，可查看目前任務及其寄送、ACK 與工作流程狀態。

    任務清單主要欄位包括建立時間、Task ID、站點／批次、問題、指派人員、workflowStatus 與明細按鈕。

    7.1 兩種狀態不能混用

    deliveryStatus 回答「通知是否送出或確認」：

    • pending：等待寄送。
    • sent：通知已送出，但尚未 ACK。
    • failed：通知寄送失敗。
    • acknowledged：工程師已確認收到。

    workflowStatus 回答「任務做到哪裡」：

    • unacknowledged：尚未有人確認收到。
    • acknowledged：已確認收到，尚未開始。
    • in_progress：工程師處理中。
    • completion_submitted：Primary 已提交完成，等待 Manager 驗收。
    • completed：Manager 已驗收完成。

    通知已寄送不代表工作已開始；要確認現場進度，必須查看 workflowStatus。

    8. 任務明細與 Manager 驗收

    按下任務列右側「明細」，會開啟 Task Detail Dialog。

    明細畫面集中顯示：

    1. Task ID、站點、問題與目前流程。
    2. 系統建議。
    3. Primary、Collaborator、必要參與及 ACK 狀態。
    4. 工程師現場回報與附件。
    5. 從建立任務開始的完整 Timeline。

    8.1 Manager 可執行的動作

    • 重送第一位未 ACK：重新寄送給尚未確認的人員；此動作會輪替安全 Token。
    • 驗收通過：只有 completion_submitted 狀態可以操作，完成後進入 completed。
    • 退回：要求工程師繼續處理，必須留下退回原因。
    • 改派或重開：用於負責人變更，或已完成任務需要再次處理的情況。

    驗收時應閱讀最新工程回報、附件與 Timeline，不應只看狀態標籤。

    9. Engineer Token 工作頁

    工程師從通知中的安全連結進入工作頁。後端會先驗證 Bearer Token，並將操作範圍限制在該工程師與該任務。

    9.1 工程師操作順序

    flowchart LR
    A[開啟安全連結] --> B[確認收到任務 ACK]
    B --> C[開始處理]
    C --> D[填寫現場回報]
    D --> E[上傳照片附件]
    E --> F{是否為 Primary}
    F -- 否 --> G[等待或繼續補充回報]
    F -- 是 --> H[提交整體完成]
    H --> I[等待 Manager 驗收]

    工程師必須先 ACK，才能開始處理。頁面上方顯示 Task、批次、風險、建議與所有指派人員；中段是現場回報；下方是既有回報與 Timeline。

    9.2 現場回報欄位

    必填欄位：

    • 觀察狀況。
    • 採取措施。
    • 處理結果。

    選填欄位：

    • 確認原因。
    • 剩餘問題。
    • 備註。

    每次最多上傳 5 張 JPG、PNG 或 WEBP。照片應能支持回報內容，例如異常位置、調整前後狀態或更換零件，不要只上傳無法判讀的遠景。

    9.3 Primary 與 Collaborator 權限

    Primary 負責整體完成提交。Collaborator 可以協助處理及提供回報，但不能代替 Primary 將任務送至 Manager 驗收。

    10. 任務閉環

    stateDiagram-v2
    [*] --> unacknowledged: Manager 建立任務
    unacknowledged --> acknowledged: Engineer ACK
    acknowledged --> in_progress: 開始處理
    in_progress --> completion_submitted: Primary 提交完成
    completion_submitted --> completed: Manager 驗收通過
    completion_submitted --> in_progress: Manager 退回
    completed --> in_progress: Manager 重開

    每次重要動作都應留下 Timeline。Task ID 是串接 Dashboard、Email、安全 Token、Assignee、Report、Attachment 與 Timeline 的追蹤鍵。

    11. 資料流怎麼走

    sequenceDiagram
    actor Manager
    participant UI as Manager UI
    participant API as Main API :8011
    participant DB as PostgreSQL
    participant Engineer as Engineer Token UI

    Manager->>UI: 選擇日期／小時／批次
    UI->>API: GET /api/manager/dashboard
    API->>DB: 查詢感測、批次與任務資料
    DB-->>API: 回傳正式資料
    API-->>UI: KPI、三站比較、建議與趨勢
    Manager->>UI: 選擇工程師並建立任務
    UI->>API: POST /api/manager/engineer-tasks
    API->>DB: 保存 Task、Assignee、Token、Timeline
    Engineer->>API: ACK、開始、回報、提交完成
    API->>DB: 更新 workflow 與工程回報
    Manager->>API: 驗收、退回、改派或重開
    API->>DB: 保存最終狀態與稽核事件

    Browser 不直接查 PostgreSQL，也不自行重算風險。Dashboard 顯示的 KPI、診斷、Recommendation 與 Trend 都由後端建立，再經前端 contract validation 後顯示。

    12. 常見狀況與處理方式

    12.1 Dashboard 顯示錯誤 Banner

    可能原因包括 API 無法連線、HTTP 回應失敗、JSON 格式錯誤、來源標記不合法或必要欄位缺失。前端會清除上一筆 KPI、站別與建議，避免把舊資料誤認成現在資料。

    處理順序：

    1. 記錄 Banner 顯示的 Endpoint、HTTP Status、Reason 與 Missing Field。
    2. 確認 Main API :8011 是否正常。
    3. 確認 PostgreSQL 與 migration 是否完成。
    4. 確認 API 回應的 responseMeta.source 與必要欄位。

    12.2 Date 或 Hour 沒有選項

    選單只顯示資料庫實際有 Sensor 資料的時段。若某日期或小時不存在，先確認資料是否已匯入，而不是在前端手動建立選項。

    12.3 趨勢圖沒有資料

    null 代表該小時缺資料，不代表數值為 0。若整天都沒有有效值，需檢查資料採集與後端 24 小時聚合結果。

    12.4 工程師沒有收到通知

    先在任務清單查看 deliveryStatus：

    • pending：檢查通知 worker 是否處理。
    • failed：檢查 Email 設定與後端錯誤。
    • sent 但未 ACK：可從任務明細重送第一位未 ACK 人員。

    12.5 工程師不能提交完成

    只有 Primary 且 workflowStatus 為 in_progress 時，才可提交整體完成。請確認工程師角色、ACK 與開始處理步驟是否正確。

    12.6 Manager 不能驗收

    只有 workflowStatus 為 completion_submitted 時，驗收通過與退回才會啟用。若仍是 in_progress，代表 Primary 尚未提交完成。

    13. 使用注意事項

    • 估算 OK／NG 與規則式診斷屬於製程風險 proxy，不是正式品檢結果或經驗證的根因模型。
    • Dashboard 預設每 20 分鐘輪詢，不是 WebSocket 即時串流。
    • PostgreSQL 是 Task、Assignee、Report 與 Timeline 的正式來源；Email 與 localStorage 不能作為稽核依據。
    • Manager API 原始路由未宣告登入 dependency。正式部署應使用內網、反向代理或 Cloudflare Access 保護 :8011 與 :8012。
    • Engineer Token 屬於安全憑證，不應轉寄給無關人員，也不應放入公開文件或截圖。

    14. 畫面與資料來源說明

    本手冊的 Dashboard、Trend Drawer 與派工 Dialog 使用專案中的 Manager UI 原始碼實際渲染。Dashboard 數值結構取自倉庫附帶的 sample_manager_dashboard.json；該檔部分中文資料值原有編碼問題，截圖時只將批次標籤、主要問題、建議與 Trend 標題替換為等義的可讀示範文字，數值、站別、時間與畫面結構未改動。
